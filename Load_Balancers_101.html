⚡ Gotchas — What the LB Does That Surprises Everyone

🚪
Fail Open Mode
If ALL targets fail health checks, ALB doesn't 503 — it keeps routing anyway.

Logic: "Assume health check misconfiguration, not real outage."

Symptom: timeouts with "100% unhealthy" hosts. Check UnhealthyHostCountRatio — we alarm on this across all 3 APX fleets.
APX: alarms on RF, Fleet1, Fleet2
⏳
Deregistration Delay = 300s Default
On deploy/scale-down, ALB waits 5 full minutes before stopping traffic to a removed host.

If your app exits in 30s → remaining 270s of requests get 502'd.

Fix: tune deregistration_delay.timeout_seconds to your actual drain time.
Deployment Risk · AWS default
🐢
Slow Start ≠ Least Outstanding Requests
Slow Start ramps new targets 0% → 100% gradually — great for JVM warm-up.

But you can't use Slow Start + LOR simultaneously.

Since APX uses LOR (ALB default), new hosts during scale-out get full traffic immediately — cold start under load.
LOR is our default · incompatible
👻
Health Check Port ≠ App Port
ALB probes port 8001. App serves on port 80. Port 8001 stays up → host marked Healthy.

Actual app is down. Traffic flows in. You get errors with "all hosts healthy."

Fix: Health check path must exercise real app functionality on the real port.
Silent Failure

🌐 DNS Pitfalls & The MaxConn Reality

Four Rules That Prevent Outages

❌

Never hardcode ALB IPs

ALB IPs change on every scale / node replacement. Hardcoded IP = stuck on a dead endpoint. Always use DNS.

⏱

Honor the 60s TTL

ELB DNS TTL is always 60s. Clients caching longer hold stale IPs for minutes after a scaling event.

🔄

Re-resolve DNS on any failed connection

On broken TCP → re-query DNS immediately, even if TTL hasn't expired. Otherwise client retries dead IP indefinitely.

📡

Exponential backoff + jitter on reconnect

1000 clients reconnecting simultaneously → thundering herd. ALB needs 1-3 min to scale. Stagger reconnects.
